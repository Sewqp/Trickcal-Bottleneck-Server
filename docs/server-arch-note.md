## 1. 문제 진단

| 항목 | 내용 |
|---|---|
| 현상 | 재접속 요청(접속 확인)이 과다 발생. 게임 방식 대비 서버가 불안정하게 터짐 |
| 1차 원인 (예측) | 하트비트 판정이 클라이언트 상태(스토리 시청 중 여부)를 반영하지 못하고, 게임 로직 요청과 분리되지 않은 채 고정 주기로만 동작함 |
| 2차 원인 (예측) | 스탯 처리가 즉시 검증·즉시 반영 구조라 DB/연산 부하가 큼. 전투력이 전체 합산 방식이라 캐릭터 1명 변경만으로도 전체 재계산 발생 |

## 2. 스토리(극장) 진입 시 접속 확인 개편

스토리는 게임 진행 중 나오는 것이 아니라 별도 화면(극장)이며, 진입 경로는 스토리 선택지 / 스토리 이어보기 선택지 두 곳으로 제한.

| 단계 | 처리 내용 | 비고 |
|---|---|---|
| 진입 THEATER_ENTER | 서버 상태 머신이 직전 상태가 STORY_SELECT / STORY_CONTINUE_SELECT인지 확인 후에만 진입 허용 | [해결] 임의 화면에서 위장 진입 차단 |
| 재생 중 (락 구간) | 1) 진입 시점 스탯 스냅샷 저장 2) 스탯 락 ON — 모든 스탯 변경 요청 거부 3) 하트비트 재접속 판정 비활성화(연결 자체는 유지, 초경량 ping/pong만 지속) 4) 스토리 관련 요청 외 전부 거부 | [해결] 원래 요청이 없어야 정상인 구간 — 부하 절감과 검증 단순화가 동시에 성립 |
| 종료 THEATER_EXIT | 1) 진입 시점 스냅샷과 현재 DB 비교 → 불일치 시 이상 신호 처리 후 DB 기준 강제 복구 2) 스탯 락 OFF, 하트비트 판정 재개 3) 스토리 클리어 보상은 이 시점 별도 트랜잭션으로 정상 반영(락과 무관) | 보상 지급은 막히지 않음 |
| 안전장치 | 1) 하드 타임아웃: 최장 재생시간 기준 여유 있게 설정 → EXIT 유실 시 자동 락 해제 2) 재로그인 시 이전 세션 락 감지되면 리셋 후 DB 기준 복구 | [주의] 크래시 · 네트워크 유실 대비 필수 |

## 3. 캐릭터 강화(마카롱) 스탯 처리 개편

전제 — 레벨에 따른 스탯 증가량은 고정 테이블(결정론적 함수). 스탯 자체를 저장할 필요가 없고, 레벨로부터 즉시 계산 가능. 검증 대상은 "레벨 상승이 정당한가" 하나로 좁혀짐.

1. UI 진입 시 — 서버가 현재 레벨(M), 마카롱 잔량(K) 전달
2. UI 이용 중 — 클라이언트가 로컬에서 소모/레벨 상승을 즉시 표시(서버 요청 없음)
3. UI 이탈 시 — 클라이언트가 최종 결과만 전송: "레벨 M → N"
4. 서버 검증 — 고정 테이블로 cost(M→N) 직접 재계산 → redis 마카롱 잔량 ≥ cost 확인 → 통과 시 redis 차감 + 레벨 갱신 → 불일치 시 거부, 서버 값 기준 롤백

| 구분 | 기존 우려 | 해결 방식 |
|---|---|---|
| 검증 기준 | 클라이언트 신고 소모량을 그대로 신뢰하는 구조는 위변조에 취약 | [해결] 신고값은 트리거일 뿐, 실제 차감량은 서버 고정 테이블 재계산 기준 |
| 요청 빈도 | 레벨업 1회당 서버 왕복 시 부하 큼 | [해결] UI 세션(진입~이탈) 단위 1회 요청으로 처리 |
| 잔량 기준 | — | 마카롱 잔량은 항상 redis(서버) 값이 기준 |
| 장비 강화 | — | 동일 논리 적용 가능 — 소모 아이템 개수 기반 서버 재계산 |

## 4. 남은 논의 항목 — 결정 사항 반영

| 항목 | 내용 | 상태 |
|---|---|---|
| 캐릭터 로드 시 스탯 | DB나 클라 캐시가 아닌 redis 값을 기준으로 통일. 로드 시점 표시값도 redis에서 조회 | DECIDED |
| 전체 전투력(패시브 합산) | 전체 재계산 대신, 스탯 처리(강화/레벨업 등) 발생 시 증가분(델타)만 redis 상의 전체 전투력 값에 더하는 방식으로 처리. redis가 전투력의 기준값 | DECIDED |
| Redis → PostgreSQL 반영 | redis는 마지막 수정 시점에 즉시 반영(항상 최신 상태 유지). PostgreSQL 반영 트리거 = 클라 lifecycle 이벤트(정상 종료) OR 서버 하트비트 타임아웃 감지(~30초, 강종·연결 끊김 포함) — 둘 중 먼저 발생하는 시점에 flush. [해결] 서버 하트비트 타임아웃은 클라 협조 없이 서버 단독으로 판단 가능 → 기존 연결 끊김 예외 처리 로직에 PG flush를 얹는 구조로, 강종 시에도 반드시 처리됨 | DECIDED |
