## 1. DB 스키마 — 신규 / 변경 테이블

기존 프로젝트의 `player`, `item_definition`/`item_instance`/`inventory` 테이블은 그대로 유지. 아래는 이번 개편에서 신규로 추가되거나 의미가 바뀌는 테이블만 정리함.

### 1-1. 캐릭터 마스터 / 보유 상태

| 테이블 | 컬럼 | 설명 |
|---|---|---|
| `character_info` (신규 · 마스터) | character_id (PK), info(이름/설명), base_stat, stat_growth_table(해시/JSONB) | 캐릭터 종류별 공용 정의. player_id 없음(전 플레이어 공유). stat_growth_table은 레벨→스탯 증가량을 담은 고정 테이블(결정론적 함수) — 스탯 자체는 저장하지 않고 레벨로부터 즉시 계산. |
| `character_status` (신규) | player_id (PK, FK), character_id (PK, FK), status SMALLINT, level INT DEFAULT 1 | 플레이어별 캐릭터 보유 상태. status 0=미보유(뽑지 못함) / 1=보유(뽑음). 계정 생성 시 전체 캐릭터에 대해 status=0 row를 미리 생성 — 캐릭터창에서 미보유 캐릭터도 함께 스크롤되어 보여야 하므로, 매번 차집합 조회 대신 player_id 단일 조건으로 전체를 한 번에 가져오기 위함. |
| `player_stat` (기존 character_stat 대체) | player_id (PK, FK), total_combat_power | 플레이어가 보유한 모든 캐릭터의 전투력 총합. 실시간 기준값은 redis, 이 테이블은 flush 시점에만 갱신되는 백업 스냅샷. |

### 1-2. 보드 시스템 (개인 / 전체 완전 분리, 보드 = 노드)

보드 하나하나가 곧 활성화 단위(별도의 "노드" 계층 없음). 캐릭터 하나당 보드가 다수 존재하며, 그 중 일부는 전체 적용 보드가 특정 캐릭터의 보드 시퀀스 사이에 배치되어 있는 구조.

| 테이블 | 컬럼 | 설명 |
|---|---|---|
| `character_board` (신규 · 마스터) | character_id (PK, FK), board_no (PK), cost, stat_type, stat_value | 캐릭터 전용(개인) 보드. 효과는 이 캐릭터 자신에게만 적용. |
| `player_character_board` (신규) | player_id (PK, FK), character_id (PK, FK), board_no (PK), status SMALLINT | 0=미해금/1=해금. 캐릭터 획득 시 그 캐릭터의 보드 전부를 status=0으로 미리 생성 (bulk `INSERT ... SELECT` 한 문장으로 — row별 개별 INSERT 금지, 1-4절 참고). |
| `global_board` (신규 · 마스터) | character_id (PK, FK), board_no (PK), cost, stat_type, stat_value | 전체 적용 보드. character_id는 효과 범위가 아니라 배치용 — 어느 캐릭터의 보드 시퀀스 안에 표시되는지를 나타낼 뿐, 효과는 보유한 캐릭터 전원에게 적용됨. |
| `player_global_board` (신규) | player_id (PK, FK), character_id (PK, FK), board_no (PK), status SMALLINT | 0=미해금/1=해금. 캐릭터 획득 시 그 캐릭터에 걸린 global_board도 함께 미리 생성 (character_board와 동일 트리거·동일 bulk insert). |

### 1-3. 설계 배경 — 두 차례 정정된 지점

① **테이블 분리 vs scope 플래그**: 개인/전체를 하나의 테이블 + 플래그 컬럼으로 합치는 안은 폐기. 전체 노드만 조회할 때 매번 조건 검사가 코드에 새는 걸 피하기 위해 테이블 자체를 분리.

② **보드 ≠ 노드+보드 2계층**: 처음에 "보드 하나에 여러 노드" 구조로 설계했던 것도 폐기 — 보드 자체가 활성화 단위이며 노드라는 별도 개념이 없음. 따라서 character_board/global_board에 노드 식별용 surrogate ID(node_id)도 불필요 — (character_id, board_no) 자연키만으로 충분.

### 1-4. 구현 유의사항 — 초기 row 생성

계정 생성(character_status) · 캐릭터 획득(player_character_board / player_global_board) 시점에 다수의 row를 한 번에 만들어야 함. row 단위로 loop를 돌며 INSERT를 개별 실행하면 왕복 비용이 누적되어 첫 로그인 · 첫 캐릭터 획득 시 체감 지연이 발생할 수 있음. 반드시 `INSERT INTO ... SELECT ... FROM` 형태의 단일 bulk INSERT 문으로 처리할 것 — PostgreSQL 기준 수백 행이라도 한 스테이트먼트면 수 ms 내로 끝남.

## 2. 전투력 계산 로직

### 2-0. 전투력 환산 공식 (확정, 2026-08-07)

**전투력 = 0.1 × HP + 2 × 메인 공격력 + 물리 방어력 + 마법 방어력**

character_board/global_board의 stat_type이 위 4개 스탯(HP·메인 공격력·물리 방어력·마법 방어력) 중 하나를 가리키며, 해금된 보드의 stat_value는 먼저 해당 스탯에 가산된 뒤 이 공식으로 전투력에 환산됨 — 즉 "보드 전투력 환산"을 보드마다 따로 계산하지 않고, 스탯 총합을 만든 다음 이 공식을 한 번만 적용.

캐릭터 전투력 = 위 공식(캐릭터 스탯[레벨 기반, character_info.stat_growth_table에서 조회] + 그 캐릭터의 활성화된 character_board 반영분 + 활성화된 global_board 전부[어느 캐릭터 밑에 배치돼 있든 무관하게 전부 포함] 반영분)

플레이어 전체 전투력(player_stat.total_combat_power) = Σ(보유한 모든 캐릭터의 전투력)

global_board 효과는 이미 각 캐릭터 전투력 계산에 개별 반영되어 있으므로, 최종 합산 시 별도로 한 번 더 더하지 않음(이중 계산 방지). global_board의 character_id는 배치 위치일 뿐 효과 대상이 아니라는 점과 일관됨.

### 2-1. 반영 방식 — 델타 누적

전체 재계산 대신, 스탯 변화(레벨업 · 보드 활성화 등) 발생 시 증가분(델타)만 redis 상의 전투력 값에 더하는 방식. redis가 전투력의 기준값이며, 캐릭터 1명 변경으로 전체를 다시 계산하지 않음. 델타 계산 시 위 공식의 계수(HP 0.1 / 메인 공격력 2 / 방어력 1)를 그대로 사용 — 스탯별 증가량 × 계수 = 전투력 증가분.

### 2-2. 이번 범위에서 제외 — 결투장 · 랭크업 시스템

구현 난이도가 높아서가 아니라, 이 프로젝트의 목적이 "게임의 병목을 지우는 것"이지 콘텐츠 폭을 넓히는 것이 아니기 때문에 명시적으로 배제. 매칭 큐 관리, 시즌·랭크 테이블 분기, 보상 정산 등 부가 로직이 핵심 아키텍처 검증(락 · 델타 누적 · redis 기준 flush)과 직접 관련 없어 이번 계획서 범위에서 뺌.

## 3. 스토리(극장) 상태 잠금 — 최소 기믹

실제 스토리 컨텐츠를 보여줄 클라이언트가 없으므로(서버만 구현), 스토리 진행 자체는 데모 성격. 전체 시나리오 구현 대신 DummyClient에 story_duration 파라미터를 추가해 THEATER_ENTER → (지정 시간 대기) → THEATER_EXIT 흐름을 트리거하는 최소 기믹으로 구현. 실제로 보여줄 가치는 스토리 내용이 아니라 아래 상태 머신 · 락 · 복구 로직 자체.

| 단계 | 처리 내용 |
|---|---|
| 진입 THEATER_ENTER | `PlayerGrain.LockAsync()`로 락 획득 시도 — 이미 락이 걸려있으면(가챠 처리 중 등) 진입 거부. 락 자체가 "극장 안인가(0/1)" 플래그를 겸함(별도 상태 필드 없음). |
| 재생 중 (락 구간) | ① 진입 시점 전투력 · 재화(골드/엘리프/마카롱) 스냅샷 저장 ② `PacketDispatcher`의 화이트리스트 게이트로 `TheaterExitRequest`/`Heartbeat`/`ReconnectRequest`/`TheaterTouchRequest` 외 모든 패킷을 핸들러 도달 전에 드롭 — 재화 변경 지점(보드 해금/강화/가챠)별로 개별 체크하지 않고 전역에서 차단. |
| 종료 THEATER_EXIT | ① 락이 안 걸려있으면 위장 진입 시도로 간주해 거부 ② 진입 시점 스냅샷과 현재 redis 값(전투력 STRING + 재화 HASH)을 Lua 스크립트 하나로 원자적 비교·불일치 시 즉시 스냅샷 값으로 복구(`tampered` 플래그로 클라에 결과 통지) ③ 락 해제. |
| 안전장치 — 하드 타임아웃 | 대사 넘기기(터치)는 클라 로컬 데이터로 진행되고 서버 왕복이 없는 구조라, **"락을 건 시각" 대신 "마지막 터치 이후 경과 시간"** 기준으로 판정(정상적으로 오래 관람 중인 플레이어를 잘못 끊지 않기 위함). 터치 시 `TheaterTouchRequest`(fire-and-forget, 응답 없음)로만 생존 신호를 보내고, `HeartbeatManager`가 5초 주기 루프 안에서 전체 세션을 대상으로 `PlayerGrain.GetLockIdleDurationAsync()`가 300초(5분) 이상이면 강제로 `DisconnectAsync()`를 호출. 극장/가챠 구분 없이 동작하는 범용 안전망(가챠는 원래 `try/finally`로 항상 unlock되어 이 경로를 타지 않음). |
| 안전장치 — 연결 종료 | 정상 종료 · 클라 강제 종료(크래시) · 서버 강제 종료 세 경우 모두 `ClientSession.DisconnectAsync()`(동일 코드 경로)에서 `PlayerGrain.UnlockAsync()`를 호출해 즉시 락 해제(멱등이라 애초에 안 걸려있었어도 안전). 재로그인 시 별도 리셋 로직은 불필요 — 연결이 끊긴 시점에 이미 언락되어 있음. |

## 4. 캐릭터 강화 스탯 처리

전제 — 레벨에 따른 스탯 증가량은 고정 테이블(결정론적 함수). 스탯 자체를 저장할 필요가 없고, 레벨로부터 즉시 계산 가능. 검증 대상은 "레벨 상승이 정당한가" 하나로 좁혀짐.

| 단계 | 처리 내용 |
|---|---|
| UI 진입 시 | 서버가 현재 레벨(M), 재화 잔량(K) 전달. |
| UI 이용 중 | 클라이언트가 로컬에서 소모/레벨 상승을 즉시 표시(서버 요청 없음). |
| UI 이탈 시 | 클라이언트가 최종 결과만 전송: "레벨 M → N". |
| 서버 검증 | 고정 테이블로 cost(M→N) 직접 재계산 → redis 재화 잔량 ≥ cost 확인 → 통과 시 redis 차감 + 레벨 갱신 → 불일치 시 거부, 서버 값 기준 롤백. 클라 신고값은 트리거일 뿐, 실제 차감은 항상 서버 고정 테이블 재계산 기준. 레벨업 1회당 왕복이 아니라 UI 세션(진입~이탈) 단위 1회 요청으로 부하 절감. |

## 5. Redis → PostgreSQL 아키텍처

redis는 마지막 수정 시점에 즉시 반영되어 항상 최신 상태를 유지하는 기준값(source of truth). PostgreSQL은 아래 4가지 트리거 시점에만 flush되는 비동기 백업 계층.

| # | Flush 트리거 | 설명 |
|---|---|---|
| 1 | 하트비트 타임아웃 | 서버가 클라 협조 없이 단독으로 판단 가능 — 기존 연결 끊김 예외 처리 로직에 flush를 얹음. |
| 2 | 클라이언트 강제 종료 | 비정상 연결 끊김(크래시 등) 감지 시. |
| 3 | 정상 종료(로그아웃) | 클라 lifecycle 정상 종료 이벤트 수신 시. |
| 4 | 서버 강제 종료(점검 등) | 서버 종료 시점에 접속 중인 전체 세션을 일괄 flush. |

### 5-1. 구현 구조

flush 로직은 신규 파일 하나에 "세션 1개 flush" 함수 단 하나만 구현. 트리거 1~3번은 이 함수를 세션 단위로 직접 호출하고, 4번(서버 강제 종료)은 SessionManager를 순회하며 동일 함수를 반복 호출하는 방식으로 재사용 — 별도의 "전체 flush" 함수를 따로 만들지 않음. 메인 코드(세션/하트비트 관리)에서는 각 트리거 발생 시점에 이 함수만 호출하면 됨.
